### 2.2 结论

**CONFIRMED：**

> D 盘（Disk 0 / Partition 4）与 E 盘（Disk 0 / Partition 6）属于同一块物理磁盘：Lexar SSD NM7A1 1TB，NVMe，GPT，Online。

这不是凭盘符或卷标推断，而是由 `Get-Partition` 的 `DiskNumber` 和 `Get-Disk` 的同一 Disk 0 信息直接确认。

### 2.3 风险含义

| 场景 | E 盘能否保护 |
|---|---|
| 单个文件误删 | 可以，若 E 上存在副本 |
| 项目目录/分区损坏 | 有一定作用 |
| 整块 Lexar NVMe 物理损坏 | **不能** |
| 整盘丢失/被盗 | **不能**，D 与 E 会一起丢失 |
| 固件/主控故障 | **不能** |
| 针对 Disk 0 的分区表/整盘操作 | **不能** |

因此，“E 盘独立备份”目前只能称为**同一物理磁盘上的分区级副本**，不是物理独立备份。

### 4.3 不能直接把 SQLite 文件复制当作正式一致性备份

当前 WAL 均为 0，表面上看复制 `.db` 文件风险较低，但依然不能把“直接复制数据库文件”定义为正式一致性备份方案：

- 若备份时应用仍在运行，可能出现写入、WAL、页缓存和 `-shm` 竞争；
- WAL 模式数据库需要确保检查点/事务边界一致；
- 直接复制 `.db`、`.db-wal`、`.db-shm` 三者不能保证形成一个可验证的快照；
- 复制后应通过 SQLite `integrity_check` 和 `foreign_key_check` 验证。

**建议正式流程：**

1. 停止应用或确认无写事务；
2. 使用 SQLite 在线备份 API / `VACUUM INTO` / 受控 checkpoint 生成一致性副本；
3. 对副本执行 `PRAGMA integrity_check`、`foreign_key_check`、`user_version` 检查；
4. 记录 SHA-256、大小、时间和 Schema；
5. 不直接以 `.db` + `.db-wal` + `.db-shm` 的裸复制作为唯一备份。

本轮不执行上述任何操作。

## 9. 最终结论

### `BACKUP_DESTINATION = CONDITIONAL_GO`

#### 可以 GO 的部分

- E 盘存在、NTFS、Fixed、Healthy；
- 可用空间 29.23 GiB，远大于项目 114.29 MiB；
- 预定目录不存在，没有当前覆盖风险；
- 可以作为本地暂存副本、快速恢复副本和校验中转。

#### 必须 CONDITIONAL 的部分

1. **E 与 D 同盘**：不能作为唯一独立备份；必须另有不同物理介质副本。
2. **未验证写入**：正式备份前必须经批准做最小写入/读取/删除验证。
3. **数据库不能裸复制**：必须使用一致性快照流程并执行完整性检查。
4. **敏感材料需保护**：`config.yaml`、`authorization.pdf`、审计日志、证据和截图应受控访问。
5. **不覆盖现有备份**：未来目录若已存在，必须新建时间戳目录，禁止覆盖。
6. **不删除历史资料**：任何历史 ZIP、验收数据库、截图、证据和文档均保留。

#### 若目标是“真正独立备份”

当前 E 盘 **不满足**物理独立性要求。需要在以下至少一种介质上再保存一份：

- 外置 USB/NVMe 硬盘（真正可离线保存）；
- 另一块内置物理磁盘；
- NAS/受控网络存储（需额外安全评估）；
- 可信离线介质。

在这些条件满足前，E 盘只能作为 **CONDITIONAL_GO 的本地副本**，不能宣称“独立备份已完成”。
